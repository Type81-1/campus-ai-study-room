## 3. 测试策略

1. **纯逻辑下沉为纯函数**：`parse_slot`、`evaluate_checkin_window`、`decide`、`score_seat`、`verify_password` 均不依赖数据库，可直接断言边界值。
2. **时间可注入**：签到窗口与违规判定接受 `now` 参数，测试不依赖真实时钟；`CHECKIN_ENFORCED` 可开关，让与时间无关的用例保持稳定。
3. **身份走真实路径**：集成用例先调 `/api/login` 拿令牌，再用 `Authorization` 头请求，不在测试里伪造 `actor`。
4. **并发用 barrier 同时起跑**：避免「伪并发」；结果同时校验状态码分布与数据库落库条数。
5. **前端真代码不变**：jsdom 加载真实 `index.html` + 真实 ES 模块，只在测试侧提供 `fetch` 与 `localStorage`，能发现选择器写错、事件没绑上这类问题。

执行命令：

```powershell
# 后端全部用例（105 个）
python -m unittest discover -s tests -t . -v

# 单个层次
python -m unittest discover -s tests -t . -p "test_security.py"
python -m unittest discover -s tests -t . -p "test_api.py"
python -m unittest discover -s tests -t . -p "test_concurrency.py"

# 并发压力测试
python scripts/loadtest.py --users 30 --rounds 3 --reads 100
```

## 5. 并发压力测试数据

执行命令：`python scripts/loadtest.py --users 30 --rounds 3 --reads 100`

| 场景 | 请求数 | 总耗时 | 吞吐 | 平均延迟 | P50 | P95 | 校验结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1-1：30 人抢同一座位 | 30 | 1.35 s | 22.3 req/s | 387.9 ms | — | 1232.0 ms | 1 成功 / 29 冲突 ✅ |
| 1-2：30 人抢同一座位 | 30 | 0.88 s | 34.2 req/s | 215.2 ms | — | 765.6 ms | 1 成功 / 29 冲突 ✅ |
| 1-3：30 人抢同一座位 | 30 | 1.13 s | 26.5 req/s | 290.9 ms | 154.5 ms | 1021.8 ms | 1 成功 / 29 冲突 ✅ |
| 2：30 人抢 30 个不同座位 | 30 | 0.69 s | 43.5 req/s | 297.4 ms | 277.3 ms | 668.0 ms | 30 全成功 ✅ |
| 3：100 次并发座位查询 | 100 | 0.37 s | 272.4 req/s | 241.7 ms | 266.6 ms | 339.3 ms | 100 全 200 ✅ |

分析：

1. **读请求 272 req/s**，是写请求的 6~12 倍——读路径没有锁竞争。v2.0 时该项为 194 req/s，v2.1 把鉴权改成只读事务后反而更快（见缺陷 D-08）。
2. **写请求 22~44 req/s**，瓶颈是 SQLite 的单写锁（所有写事务串行）。迁移到 MySQL（InnoDB 行锁）后不同座位的写可并行，预期明显提升，需在真实实例上复测。
3. 所有场景**结果校验通过**，没有超卖或重复预约，说明并发控制有效，而不是靠低并发掩盖问题。

## 6. 缺陷记录与修复

| 编号 | 问题 | 影响 | 处理 |
| --- | --- | --- | --- |
| D-01 | 「查冲突 → 插入」不在同一事务 | 并发下双订同一座位 | 写事务内锁座位行；新增 C-01 回归 |
| D-02 | SQLite 开 WAL 后并发 `BEGIN IMMEDIATE` 报 `readonly database` | 并发下大量 500 | 改用回滚日志 + `busy_timeout` 串行化写入 |
| D-03 | `HTTPServer` 默认 listen backlog 为 5 | 并发响应出现约 1 秒尖刺 | 自定义 `StudyRoomServer.request_queue_size = 128` |
| D-04 | SQLite `CURRENT_TIMESTAMP` 取 UTC | 违规时间窗口偏差 8 小时 | 建表默认值改 `datetime('now','localtime')`，签到时间由应用写入 |
| D-05 | `/api/seats` 逐座位查冲突（N+1） | 读接口放大 | 改为一次查出占用集合 |
| D-06 | 重复扫描重复生成违规 | 违规列表重复 | 状态先流转 + `(reservation_id, kind)` 唯一键兜底 |
| D-07 | `expired` 与 `seats.status` 是死字段 | 状态机与代码不一致 | 扫描产生 `expired`；`seats.status` 用于维护中并参与校验 |
| D-08 | 鉴权在请求路径上用写事务更新 `last_seen_at` | 每个请求都抢 SQLite 写锁，读吞吐跌到 37 req/s、P95 2.2 s | 鉴权改只读事务，令牌改为绝对有效期；读吞吐回到 272 req/s |
| D-09 | 超时签到在事务内 `raise` | 事务回滚会把刚写入的违规记录撤销 | 改为「先提交事务，再抛业务异常」 |
| D-10 | 管理看板切换页签不重新拉数据 | 页签显示空白直到手动刷新 | 切换时调用 `refresh()`；由前端冒烟测试发现 |
| D-11 | 旧 `app.js` 25 行压缩代码不可读 | 无法维护、选择器写错难排查 | 重写为 ES 模块，并用 jsdom 冒烟测试兜底 |

## 7. 遗留问题与风险

| 项 | 说明 | 计划 |
| --- | --- | --- |
| MySQL 实机压测未执行 | 本机无 MySQL 服务与 Docker。MySQL 侧的方言翻译、脚本切分、`TIME` 字段归一化已由 `test_dialect.py` 覆盖，但连接池与 `FOR UPDATE` 未在真实实例上跑压力测试 | 部署环境执行 `docker compose up -d` 后重跑 `scripts/loadtest.py` 补充数据 |
| 令牌存在 `localStorage` | 若前端出现 XSS，令牌可被读取 | 课程范围外；可改为 `HttpOnly` Cookie + CSRF Token |
| 无登录失败限流 | 可被暴力枚举口令 | 可加 IP/账号维度的失败计数与锁定 |
| SQLite 写吞吐上限 | 约 20~45 req/s | 生产使用 MySQL；SQLite 仅用于本地演示与测试 |
| 前端无真实浏览器测试 | jsdom 覆盖了逻辑与渲染，但未验证 CSS 布局与跨浏览器兼容 | 可补 Playwright 截图对比 |
| 演示账号口令仍打印在登录页 | 便于验收演示，但不符合生产习惯 | 交付版可改为构建期注入或直接移除提示 |

## 8. 结论

1. **105 个后端用例全部通过**：单元 49、集成 53、并发 3；另有 25 项前端无头检查全部通过。
2. **P1 安全项全部落地**：令牌鉴权替代 `user_id` 传参、口令 PBKDF2 哈希、越权访问回归用例、签到时间窗口、座位维护与用户概览。
3. 任务书要求的预约冲突、签到失效、权限越界、违规占座四类异常场景均有专项用例，并发场景验证了**不会超卖**。
4. 过程中发现并修复了 4 个 v2.1 自身引入的问题（D-08~D-11），其中 D-08 让读吞吐从 37 提升到 272 req/s，说明压测确实能暴露设计缺陷。
5. 剩余风险集中在部署环境（MySQL 实机）与前端安全加固，均不影响课程验收。
