## 3. 测试策略

1. **纯逻辑下沉为纯函数**：`parse_slot`、`evaluate_checkin_window`、`decide`、`score_seat`、`heat_label`、`verify_password` 均不依赖外部状态，边界值可精确断言。
2. **时间可注入**：签到窗口与违规判定接受 `now` 参数；`CHECKIN_ENFORCED` 可开关，使与时间无关的用例保持稳定。
3. **身份走真实路径**：集成用例先调 `/api/login` 拿令牌，再用 `Authorization` 头请求，不在测试中伪造 `actor`。
4. **SSE 用裸 socket 验证**：直接连接真实服务，检查状态行、`text/event-stream`、chunked 分帧、首帧、事件推送与心跳，避免"只测了函数没测协议"。
5. **并发用 barrier 同时起跑**：结果同时校验状态码分布与数据库落库条数。
6. **前端双保险**：jsdom 验证逻辑与选择器（快），Playwright 验证真实渲染与像素基线（真）。

python scripts/loadtest.py --users 30 --rounds 3 --reads 100

### 4.7 MySQL 实机验证（v2.2 补充）

本机安装了 MySQL 8.0.40 便携版（`D://MySQL`，端口 3307），本轮补上实机数据：

| 检查项 | 命令 | 结果 |
| --- | --- | --- |
| 建表与引擎 | `python scripts/mysql_check.py` | 5 张表、29 个索引，`reservations` 为 InnoDB ✅ |
| 行锁并发 | 同上 | 两人同抢一个座位 → `[201, 409]` ✅ |
| 20 线程压测 | 同上 | 20/20 成功，41.7 req/s ✅ |
| **整套用例** | `TEST_DB_BACKEND=mysql python -m unittest discover -s tests -t .` | **130 / 130 通过**（含 3 个并发用例）✅ |
| HTTP 全链路 | 服务以 MySQL 启动后调 `/api/health`、登录、下单、查询 | 正常，health 显示 `mysql://root@127.0.0.1:3307/campus_study_room` ✅ |

**实机立刻抓出一个 SQLite 上测不到的缺陷**：两人抢同一座位时双方都返回 201（双订）。原因是 MySQL 默认 `REPEATABLE READ` 在事务第一次普通读时就固定了快照，而创建预约当时是「先查违规阈值（普通读）→ 再加锁 → 再查冲突」，冲突检查读的是旧快照，看不到对方刚插入的预约。修复与验证见 D-18。

MySQL 压测数据（30 并发，`python scripts/loadtest.py`）：

| 场景 | 吞吐 | 平均延迟 | P95 | 对比 SQLite |
| --- | --- | --- | --- | --- |
| 抢同一座位（预热轮） | 56.6 req/s | 442.0 ms | 524.4 ms | 首轮含连接池预热 |
| 抢同一座位（稳定轮） | 360.7 / 373.9 req/s | 50.0~52.3 ms | 73.2~76.7 ms | **写吞吐约为 SQLite 的 10 倍** |
| 30 人抢 30 个不同座位 | 283.7 req/s | 65.0 ms | 99.8 ms | 行锁并行生效 |
| 100 次并发座位查询 | 313.8 req/s | 166.3 ms | 292.8 ms | 略优于 SQLite（290 req/s） |

结论：SQLite 的单写锁确实是写吞吐瓶颈（28~40 req/s），换到 InnoDB 行锁后写吞吐提升到 283~374 req/s，且并发抢座仍严格只有 1 个成功。

## 5. 并发压力测试数据

执行命令：`python scripts/loadtest.py --users 30 --rounds 3 --reads 100`

| 场景 | 请求数 | 总耗时 | 吞吐 | 平均延迟 | P50 | P95 | 校验结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1-1：30 人抢同一座位 | 30 | 0.87 s | 34.6 req/s | 271.6 ms | — | 747.9 ms | 1 成功 / 29 冲突 ✅ |
| 1-2：30 人抢同一座位 | 30 | 0.96 s | 31.2 req/s | 240.9 ms | — | 835.9 ms | 1 成功 / 29 冲突 ✅ |
| 1-3：30 人抢同一座位 | 30 | 1.05 s | 28.6 req/s | 285.1 ms | — | 934.0 ms | 1 成功 / 29 冲突 ✅ |
| 2：30 人抢 30 个不同座位 | 30 | 0.75 s | 39.8 req/s | 292.9 ms | 281.8 ms | 646.8 ms | 30 全成功 ✅ |
| 3：100 次并发座位查询 | 100 | 0.34 s | 290.5 req/s | 215.6 ms | 238.3 ms | 308.6 ms | 100 全 200 ✅ |

分析：

1. 读请求 290 req/s，约为写请求的 7~10 倍——读路径无锁竞争；鉴权走只读事务是关键（v2.1 曾因鉴权写锁把读吞吐压到 37 req/s）。
2. 写请求 28~40 req/s，瓶颈是 SQLite 单写锁；MySQL InnoDB 行锁下不同座位可并行，需在实机复测（第 7 节）。
3. 全部场景结果校验通过，未出现超卖。

## 6. 缺陷记录与修复

| 编号 | 问题 | 影响 | 处理 |
| --- | --- | --- | --- |
| D-01 | 「查冲突 → 插入」不在同一事务 | 并发双订 | 写事务内锁座位行 |
| D-02 | SQLite 开 WAL 后并发 `BEGIN IMMEDIATE` 报 `readonly database` | 并发 500 | 回滚日志 + `busy_timeout` |
| D-03 | `HTTPServer` 默认 backlog 为 5 | 约 1 秒延迟尖刺 | `request_queue_size = 128` |
| D-04 | SQLite `CURRENT_TIMESTAMP` 取 UTC | 违规时间窗口偏 8 小时 | `datetime('now','localtime')` + 应用层写入 |
| D-05 | `/api/seats` 逐座位查冲突（N+1） | 读接口放大 | 一次查占用集合 |
| D-06 | 重复扫描重复记违规 | 数据重复 | 状态先流转 + 唯一键兜底 |
| D-07 | `expired` 与 `seats.status` 死字段 | 状态机与代码不一致 | 扫描产生 `expired`；`seats.status` 参与预约校验 |
| D-08 | 鉴权用写事务刷新 `last_seen_at` | 读吞吐跌至 37 req/s | 改只读事务 + 绝对有效期（回到 290 req/s） |
| D-09 | 超时签到在事务内 `raise` | 事务回滚撤销违规记录 | 先提交再抛业务异常 |
| D-10 | 管理看板切换页签不刷新 | 页签空白 | 切换时 `refresh()` |
| D-11 | 旧 `app.js` 25 行压缩代码不可读 | 无法维护 | 重写为 ES 模块 + jsdom 冒烟兜底 |
| D-12 | 冷门座位因子在历史不足时对所有座位加分 | 因子失效、白送 5 分 | 仅当人均 ≥ 1 时启用，并补单测 |
| D-13 | 提示条固定右上角，遮挡日期与实时徽标 | 顶栏信息被盖住 | 改为右下角弹出 |
| D-14 | 管理看板标题重复（顶栏 + 区块） | 视觉重复 | 去掉区块标题，仅保留说明 |
| D-15 | 趋势图横轴显示 `2026-…` | 日期被截断不可读 | 传 `MM-DD` 标签 |
| D-16 | 420px 窄屏品牌文字溢出、表格撑破页面、按钮竖排 | 移动端不可用 | 隐藏品牌文字、`min-width:0`、表格容器内滚动、按钮 `nowrap` |
| D-17 | 未提供 favicon 导致控制台 404 | E2E 控制台检查失败 | 新增 `favicon.svg` 并在页面声明 |
| D-18 | **MySQL 下并发抢同一座位出现双订**：`REPEATABLE READ` 在事务首次普通读时固定快照，冲突检查读到旧数据 | 座位被订两次（SQLite 测不出） | ① 锁座位改为事务第一条语句；② MySQL 连接统一 `READ COMMITTED`；③ 修正后 `[201, 409]`，130 用例在 MySQL 全绿 |
| D-19 | 给冲突查询加 `FOR UPDATE` 后，并发插入出现大量 `Deadlock found (1213)` | 20 线程里 12 个失败 | 去掉冲突查询的 `FOR UPDATE`（座位行锁已串行化），改为 `READ COMMITTED` 保证读最新数据 |
| D-20 | MySQL 上跑测试时用例批量 404 | `DELETE` 不重置自增，用例按 id 1~24 引用座位时取不到 | 测试夹具在清表后 `ALTER TABLE ... AUTO_INCREMENT = 1` |

> D-12~D-17 均由本轮新增的 Playwright / 单测发现，说明「真实渲染 + 像素基线」能抓到 jsdom 抓不到的样式问题。

## 7. 遗留问题与风险

| 项 | 说明 | 计划 |
| --- | --- | --- |
| MySQL 便携版不注册服务 | `D://MySQL` 为 ZIP 便携版，开机不自启，关掉控制台窗口即停库 | 需要常驻可 `mysqld --install` 注册服务；日常演示用 `start-mysql.bat` 即可 |
| 令牌存 `localStorage` | XSS 场景可被读取 | 课程范围外；可改 `HttpOnly` Cookie + CSRF |
| 无登录失败限流 | 可被暴力枚举 | 可加 IP/账号维度失败计数 |
| SSE 单进程 | 事件总线为进程内实现，多进程部署需换 Redis Pub/Sub | 接口不变，替换 `EventBus` 实现即可 |
| SQLite 写吞吐上限 | 约 30~40 req/s | 生产用 MySQL |
| 浏览器矩阵有限 | 仅 Chrome/Edge（Chromium 内核）实机验证 | 可补 Firefox/WebKit |

## 8. 结论

1. **130 个后端用例全部通过**（单元 66 / 集成 55 / SSE 6 / 并发 3），前端 25 项冒烟 + 22 项 E2E 检查全部通过。
2. 任务书要求的四类异常场景（预约冲突、签到失效、权限越界、违规占座）均有专项用例；并发场景验证不会超卖。
3. 新增的 SSE 通道经过协议级验证（分帧、心跳、鉴权、事件载荷），前端 1 秒内可见他人操作结果。
4. 推荐 v2 的六个评分因子全部可解释且可单测，时段热度以提示形式呈现，不污染排序。
5. 本轮通过 Playwright 真实渲染发现并修复 6 个样式/交互缺陷（D-12~D-17），并建立截图基线，后续改版可回归。
6. **MySQL 实机已补齐**：130 个用例在 MySQL 8.0.40 上全绿，行锁验证 `[201, 409]`，写吞吐达到 SQLite 的约 10 倍；过程中发现并修复了 3 个只在 MySQL 上暴露的问题（D-18~D-20），说明「单库测试通过」不能替代交叉验证。
