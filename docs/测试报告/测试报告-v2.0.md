## 3. 测试策略

### 3.1 分层策略

- **纯逻辑下沉为纯函数**（`slot_rules.py`、`violation_service.decide`、`recommendation_service.score_seat`），不依赖数据库与时间，可直接断言边界值。
- **接口层测试直接调用 `Api.handle`**，与 HTTP 层等价但不占用端口，便于反复执行与 CI。
- **并发用例用 `threading.Barrier` 制造同时起跑**，避免伪并发。
- **时间相关规则注入 `now` 参数**，消除对真实时钟的依赖，结果可复现。

### 3.2 执行命令

```powershell
# 全部用例
python -m unittest discover -s tests -t . -v

# 单个层次
python -m unittest discover -s tests -t . -p "test_slot_rules.py"
python -m unittest discover -s tests -t . -p "test_api.py"
python -m unittest discover -s tests -t . -p "test_concurrency.py"

# 并发压力测试
python scripts/loadtest.py --users 30 --rounds 3 --reads 100
```

## 5. 并发压力测试数据

执行命令：`python scripts/loadtest.py --users 30 --rounds 3 --reads 100`

| 场景 | 请求数 | 总耗时 | 吞吐 | 平均延迟 | P50 | P95 | 最大 | 校验结果 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1-1：30 人抢同一座位 | 30 | 0.98 s | 30.5 req/s | 351.2 ms | — | 860.3 ms | — | 1 成功 / 29 冲突 ✅ |
| 1-2：30 人抢同一座位 | 30 | 0.82 s | 36.8 req/s | 230.2 ms | 192.6 ms | 694.3 ms | 804.8 ms | 1 成功 / 29 冲突 ✅ |
| 1-3：30 人抢同一座位 | 30 | 0.85 s | 35.4 req/s | 226.7 ms | 159.3 ms | 714.9 ms | 816.7 ms | 1 成功 / 29 冲突 ✅ |
| 2：30 人抢 30 个不同座位 | 30 | 1.06 s | 28.2 req/s | 399.8 ms | 332.2 ms | 958.4 ms | 1055.0 ms | 30 全成功 ✅ |
| 3：100 次并发座位查询 | 100 | 0.51 s | 194.2 req/s | 286.6 ms | 331.5 ms | 452.3 ms | 468.1 ms | 100 全 200 ✅ |

分析：

1. **写请求吞吐约 28–37 req/s**，受限于 SQLite 的单写锁（所有写事务串行）。这是选型决定的，不是代码缺陷；迁移到 MySQL（InnoDB 行锁）后，不同座位的写可以真正并行，预期提升明显。
2. **读请求吞吐 194 req/s**，是写请求的 5–6 倍，说明读路径没有额外的锁竞争。
3. 所有场景**结果校验全部通过**，没有出现超卖或重复预约，说明并发控制策略有效，而不是「靠低并发掩盖问题」。

## 6. 缺陷记录与修复

测试过程中发现并修复的问题：

| 编号 | 问题 | 影响 | 处理 |
| --- | --- | --- | --- |
| D-01 | 原实现的「查冲突 → 插入」不在同一事务，并发下可双订同一座位 | 座位超卖 | 写事务内锁座位行后再查冲突；新增 C-01 回归用例 |
| D-02 | SQLite 开启 WAL 后，Windows 上并发 `BEGIN IMMEDIATE` 报 `attempt to write a readonly database` | 并发下大量 500 | 改用回滚日志 + `busy_timeout` 串行化写入；压力测试复测通过 |
| D-03 | `HTTPServer` 默认 listen backlog 为 5，几十个连接同时到达出现约 1 秒延迟尖刺 | 并发响应时间劣化 | 自定义 `StudyRoomServer`，`request_queue_size = 128` |
| D-04 | SQLite 的 `CURRENT_TIMESTAMP` 取 UTC，与本地业务时间相差 8 小时 | 违规时间窗口计算偏差 | 建表默认值改 `datetime('now','localtime')`，签到时间由应用层写入本地时间 |
| D-05 | `/api/seats` 原实现对每个座位单独查一次冲突（24 次查询） | N+1 查询，读接口放大 | 改为一次查出占用座位集合 |
| D-06 | 重复扫描会重复生成违规记录 | 违规列表重复 | 扫描前先改预约状态（不再命中待扫描集合）+ `violations(reservation_id, kind)` 唯一键兜底 |
| D-07 | `expired` 状态与 `seats.status` 字段从未被写入（死字段） | 状态机与代码不一致 | 引入违规扫描后 `expired` 由规则产生；`seats.status` 用于「维护中」并参与预约校验 |

## 8. 结论

1. 单元测试 41 个（含方言适配与双库脚本一致性检查）、接口集成测试 39 个、并发测试 3 个，**共 83 个用例全部通过**，任务书要求的「单元测试 + 集成测试 + 并发场景压力测试」三项均已落地。
2. 预约冲突、签到失效、权限越界、违规占座四类异常场景均有专项用例覆盖，且并发场景验证了**不会超卖**。
3. 新增的违规预警链路（超时未签到 / 超时占用 → 状态流转 → 违规记录 → 限制预约 → 管理员处理后可恢复）端到端可用。
4. 当前瓶颈是 SQLite 的单写锁，属于选型限制；MySQL 迁移完成后需在真实实例上复测并补充第 5 节数据。
